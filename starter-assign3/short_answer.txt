Q1. Looking at a call stack listing in a debugger, what is the indication that the program being debugged uses recursion?
A1. The indication that the program we're debugging uses recursion is that, in the call stack, we see that factorial(int) is called on multiple levels. Since we know that each entry in the call stack corresponds to a function that has been called and hasn't executed yet, we can see that factorial(int) has been called by itself multiple times, which is the definition of recursion. 

Q2. Subtract the innermost level number from the outermost to get the maximum count of stack frames that fit in the capacity of the call stack. How many stack frames fit in your system's call stack?
A2. Outermost level number: 16284, Innermost: 1. Outermost - Innermost = 16284 - 1 = 16283. 16283 stack frames fit in our system's call stack. 

Q3. Describe how the symptoms of infinite recursion differ from the symptoms of an infinite loop.
A3. Infinite recursion results in a stack overflow error in QT Creator while infinite loops just keep running and need to be manually terminated. 

Q4. In place of selecting values over a defined range, an alternate approach would be to randomly select values for base and exponent. Such a test case would test something different each time you ran it. This test approach is part of a larger approach known as "fuzz" testing. What do you see as possible benefit and downside of randomness being used in a test case?
A4. A possible benefit to randomly generating numbers for our bases and exponents in test cases is that we can cover a wider breadth of possible runs. However, targeted cases like skipping certain input values or testing the program specifically on a certain kind of number is not possible with such a randomized test function.

Q6. Explain how the recursive structure of `recPower` results in a Big-O runtime of `O(logN)` relative to the size of its `exp` argument.
A6. The recursive structure of `recPower` results in a Big-O runtime of `O(logN)` because the line (double half = recPower(base, exp/2)) cuts our exponent in half, and that also cuts our runtime by half every time the recursive function is called. Following Big-O logic, when we split the runtime like that, the Big-O runtime is defined as O(logN).

Q8. Give a rough estimate of the maximum length sequence that could be successfully merged on your system assuming a recursive implementation of `binaryMerge`.
A8. Call stack fits 16,283 frames. A recursive binaryMerge would use one stack frame for each element it merges, longest sequence we could merge is about 16,000 elements total.

Q9. What would be the observed behavior if attempting to recursively merge a sequence larger than that maximum?
A9. Stack overflow. It would just quit with no error message, the same way factorial(-3) did in the warmup.

Q13. You run `recMultiMerge` on a sequence of size 1 million and see that it completes just fine. Explain why this is not running afoul of the call stack capacity limitation.  _Hint_: How many stack frames (levels) are expected to be on the call stack at the deepest point in the recursion in `recMultiMerge`?
A13. recMultiMerge cuts the list of queues in half each time, so the recursion is only about log₂(k) levels deep. Even if all 1 million elements started in their own queue (k = 1,000,000), that’s only 20 levels. 20 frames is nowhere near our previous limit of about 16,000. Also, binaryMerge uses a loop, so it doesn’t add a frame for each element.
